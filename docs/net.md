# Multiplayer netcode (`src/net/`)

## Overview

This is the first multiplayer step the owner chose: **a game protocol, a server loop and a client, tested over a pretend network with delay, loss and reordering**, first over a pretend network and then **over real UDP sockets**. It runs the game's own player movement on a server and on up to four clients and keeps them in step. A **dedicated server program and a test bot** exist and play each other over real packets. **The running game does not use any of it yet** (`main.c` is untouched; there is no menu to host or join), so nothing about single-player can have changed.

What exists:

- a **wire format** (`net_wire`, `net_proto`): bytes in and out of a buffer with every access checked, and five messages (Hello, Welcome, Disconnect, Input, Snapshot);
- a **transport seam** (`net_transport.h`): the only thing the server and client know about the network;
- a **pretend network** (`net_loopback`): delay, jitter, loss, doubling, reordering, blackouts, with a fixed random generator so a run is the same every time;
- the **movement simulation** both ends share (`net_move_sim`): the real `PlayerStep`, jump and slide, from a rounded command;
- an **authoritative server** (`net_server`) and a **predicting client** (`net_client`).
- a **reliable-message layer** (`net_reliable`): whole messages, in order, exactly once, over any datagram path that loses, doubles and reorders;
- a **real transport** (`net_udp`): UDP sockets under the same seam, with the reliable layer on top, for a LAN or a server with an open port;
- a **server program and a test bot** (`src/server/`, `scripts/build_server.sh`), and a smoke test that runs them as separate processes.

### The architecture decision, and what it leaves open

The protocol, the server loop and the client logic are **C**, written against the small transport interface. There are now two transports behind it: the **pretend network** (tests) and **real UDP** (`net_udp`), which carries datagrams as UDP packets and reliable messages through a small reliable layer of our own (`net_reliable`). Reasons for plain UDP now: it needs nothing but the C library (so it builds on a phone in Termux, on Android and on a desktop), the sandbox can test it over real sockets, and the stated way to play (the same Wi-Fi, or a machine with an open port) needs no more. Its limits are real: **no encryption and no proof of who is who** (see Known limits), and a browser cannot use it at all (no UDP in a page).

**mid-net is the transport the owner wants, and the native one is connected** (`net_mid.h`, below): QUIC gives encryption and a way through more networks, and it is the owner's own engine, so it can be improved as the game grows. It plugs in behind the same interface through a new C-interface crate in mid-engine (`mid-net-transport-quinn-ffi`). Plain UDP with the game's own reliable layer stays as the fallback and as what the tests of the protocol run on (it builds with nothing but a C compiler). Still open: **the browser** (WebTransport needs a secure page and a certificate the browser accepts, and a separate wasm module next to the Emscripten build; a WebSocket dev transport is the alternative) and **the Android build** (the build script cross-compiles the Rust library for armv7 and links it into the APK: the cross-compile has built on GitHub, the final link and a run on a phone have not been seen yet: `android.md`). Nothing in the server or client changes when a transport is swapped.

## The protocol (`net_proto.h`)

Two channels, as a QUIC connection gives: **datagrams** that may be lost, doubled and reordered (Input, Snapshot), and a **reliable ordered** channel (Hello, Welcome, Disconnect). A packet starts `'T' 'B'` and a kind byte.

| Message | Direction | Channel | Size | What it carries |
|---|---|---|---|---|
| Hello | client to server | reliable | 17 B | protocol version, the chosen character id |
| Welcome | server to client | reliable | 27 B | version, tick rate, the player's id, the floor's seed and number, the server's tick, the spawn |
| Input | client to server | datagram | 40 B | the tick, the newest snapshot seen, and **four commands** (that tick and the three before it) |
| Snapshot | server to client | datagram | 71 to 125 B | the tick, whether the player has started, how early the newest command came, the owner's full movement state, up to three other players (rounded) |
| Disconnect | either | reliable | 4 B | a reason (normal, version, full, timeout, bad) |

A **command** (`NetCmd`, 7 bytes) is one tick of the player's wishes already rounded to what the wire carries (stick to a 127th, yaw to a 65536th of a turn, pitch to a 32767th of 89 degrees, eight buttons): **both ends run the game from the rounded command**, so the client's prediction and the server's simulation start from the same numbers. The buttons already include fire, use, swap and light, which this slice does not use yet.

The **owner's state** is sent as full floats (15 of them) and not rounded, because a rounded state could not be run on from; other players are told rounded millimetres.

**Decoding is strict**: wrong magic, an unknown kind, a short packet, a byte too many, a count over its limit, a NaN or infinity, an unknown flag bit, a character id that is not lowercase letters, digits and `_`, a player id out of range: all refused. Tested by cutting every message at every length, spoiling bytes, 300000 random and spoilt packets (what is accepted must re-encode to exactly the same bytes), and the whole test under AddressSanitizer and UndefinedBehaviorSanitizer with no finding.

**Bandwidth** at 30 snapshots a second: about 1.2 KB/s up and 2.1 to 3.8 KB/s down per client (full snapshots, no deltas yet).

## How it works

### The server (`net_server.c`)
It owns the floor (made from the seed, as every client makes it) and every player. **It never takes a position from a client**, only commands. Each tick (30 Hz, driven by the caller): for each player it takes the command that arrived for this tick and steps the player with `NetSim_Step`; then it sends every client a snapshot.

- A command carries the tick it is for. One **already past** is late (refused, counted); one **more than 20 ticks ahead** is refused (a flooded or forged clock); a **second command for a tick** is ignored (the first wins, so repeating a command does not move the player twice).
- A command that **did not arrive in time** is replaced by the last one for 5 ticks (one-off presses removed), then by standing still (the aim kept), then the client is dropped after 5 seconds of silence.
- The player is **not run until its first command arrives** (it starts at that command's tick), so the client and the server begin from the same state.
- It reports back **how early** the newest command came (`margin`, in ticks, negative when late). That is what the client tunes its clock by.
- **Limits:** at most 64 packets per client per poll (a flood waits, the tick is never held up), a stranger's packets counted and thrown away. **A connection that has not said Hello within 3 seconds is dropped**, so strangers cannot hold the four places.

### The client (`net_client.c`)
- **Prediction.** It runs its own player the moment the player acts, with the same `NetSim_Step`, keeps the last 64 ticks of commands and resulting states, and sends each command at once, repeated in the next three packets, so a lost packet is nearly always covered by the next (measured: 0.2% of commands missing at their tick at 20% loss).
- **Reconciliation.** A snapshot for tick T carries the server's state after tick T. The client compares it with its own record of tick T. Within 2 cm (and the same stamina, speed and slide state): nothing to do. Otherwise it **puts the server's state back and runs its own commands since again** to the present, so a correction is a change of the present and not a rubber band back in time. The jump that makes is **not shown**: the drawn position is the predicted one plus a difference that fades away (85% kept each tick), unless it is over two metres (a teleport, a respawn), which is shown as it is.
- **The clock.** Its tick count runs ahead of the server's (at first by the measured round trip plus 3 ticks) so a command is there before the server needs it. If the worst margin of the last 20 snapshots is below 1 it runs 5% faster, above 4 5% slower, until it is back in range (tested: a route that gets 8 times slower makes 48 commands late once, then none; when it is fast again the lead falls from 8 ticks to 6).
- **Other players** are drawn **100 ms in the past**, between the two snapshots that surround that time; with no newer snapshot they are held where they were last seen.

## Modules

### `net_wire.h` and `net_wire.c`
`NetW` and `NetR`: little-endian whatever the machine, every access checked. A writer that runs out of room, or a reader asked for more than is left, sets an error and goes on harmlessly; nothing is read or written outside the buffer. `NetR_Done` is true only when nothing went wrong and every byte was read.

### `net_proto.h` and `net_proto.c`
The messages above, `NetProto_Encode` and `NetProto_Decode`, and the command rounding (`NetCmd_Make`, `NetCmd_Move` which holds the length to 1 so a forged (127, 127) is no faster walk, `NetCmd_Yaw`, `NetCmd_Pitch`). The tick rate (30), the datagram limit (1200 bytes), the player limit (4) and the redundancy (4) are here.

### `net_transport.h`
`NetTransport`: send and receive of datagrams and of reliable messages, as function pointers, and an optional `close` (the connection is finished with: a real transport lets a Disconnect still in flight get out, then frees the connection). Nothing else of the network is known.

### `net_reliable.h` and `net_reliable.c`
Whole messages, in order, exactly once, over a path that loses, doubles and reorders packets. One `NetRel` per connection; it knows nothing of sockets (it hands the bytes to send to an emit function, is given the bytes that arrive, and is told the time), so it is tested over the pretend network with a made-up clock.

- **A window of 32 messages in flight**, each with a sequence number (16 bits, wrapping: tested over 70,000 messages), each resent with a growing wait until acknowledged. Messages are small (512 bytes at most): this carries the handshake and rare events, not a stream.
- **Acknowledgements are cumulative plus a bitmap of the next 32**, so a lost message does not make the ones after it wait (tested: with message 1 of 5 lost, only message 1 is sent again).
- **The wait** is the measured round trip plus four times its swing (only from messages sent once, so a resend does not confuse the measure), never under 40 ms, doubling each resend up to a second. After 12 sends of one message with no answer the connection is called dead (about 11 seconds on a dead path).
- **Flow control comes free**: a receiver that does not read holds one window and refuses the next; the sender stops at two windows and nothing is lost.
- It refuses a false acknowledgement (of messages never sent), an old copy is answered and not delivered again, and malformed packets are refused (tested with 200,000 random ones, under the sanitizers).

### `net_udp.h` and `net_udp.c`
The real network: `NetUdpHost`. A **server** listens on a UDP port (0 picks a free one) on every address of the machine and serves up to 8 connections from one socket; a **client** connects to an IPv4 address or name. Every packet starts with a **32-bit connection id** the client picks, then a kind byte (a datagram, or the reliable layer's data or acknowledgement), so one socket tells many players apart.

- **A connection opens** only when a server receives the *first reliable message of a connection* (a reliable data packet, sequence number 0, with something in it): the Hello. A random packet passes that about once in sixteen million; datagrams and later-numbered packets from a stranger open nothing. `NetUdpHost_Accept` hands the new connection to the game once.
- **A packet is accepted for a connection only from that connection's address** (a stranger who learns an id cannot speak for it; tested). Each connection keeps at most 32 datagrams waiting for the game to read (the rest are counted and dropped).
- **The transport's receive functions read the socket themselves**, so a game that only polls its transports needs nothing more than `Accept`.
- **Closing** lets the last message (a Disconnect) get out: the connection is kept up to two seconds until it is acknowledged, then freed. A connection is freed only when the game closes it (the server does when it drops a client or refuses a full house); there is no idle timeout of its own, so a connection a game forgets to close stays.
- `NetUdp_SetDebug(loss, double)` makes every packet sent be lost or sent twice with those chances: for tests and for trying the game on a bad network (`--loss` on the server and the bot).
- Only where `TOWER_NET_UDP` (platform.h: Android and desktop); elsewhere every function says "no network", so the web build links and does nothing. A phone needs the INTERNET permission in the Android manifest to use this; it is declared now (`android/AndroidManifest.xml`), though nothing in the app calls the network yet.

### `net_discovery.h` and `net_discovery.c`
**What it does:** finding a game on the local network without typing an address (the lobby screen FIND GAMES lists the result, `lobby.md`). The idea, and the phone knowledge in it, come from the `LocalLobbyManager` of the owner's Unity package `com.midmanstudio.netcode` (MidManStudio_Unity). A **searcher** sends a small question to the network (the limited broadcast address, the directed broadcast address of every usable interface, and this machine itself); a **host** listening on the question port (7778 by default, beside the game's 7777) answers the sender directly with where to connect and who is playing; the searcher lists what answered, drops what has not been heard for 5 seconds and asks again every 2. The game's own handshake (Hello and Welcome, `net_proto.h`) does the rest. The packets, the table of lobbies and the address helpers need no sockets and are tested without them; the sockets exist only where `TOWER_NET_UDP` (elsewhere every function says "no network": a browser has no UDP and cannot search; it needs an address typed in). IPv4 only.

- **The packets** (little-endian, through `net_wire`). A question: the magic `TWD1`, a version, kind 1, a 32-bit nonce, then zeros up to **exactly 64 bytes**. An answer: the magic, version, kind 2, the nonce echoed, the game's protocol version, the game port, players, places, **the transport the host speaks** (0 plain UDP, 1 QUIC: `net_transport.h`), a host id, and a name of 1 to 24 printable ASCII characters (at most 46 bytes). Both decoders are strict, and **whatever they accept encodes back to the very same bytes** (checked on 300,000 random and spoilt packets, and every cut and every flipped bit of a good one).
- **Nobody can use a host to send more than they sent it.** A question is padded to 64 bytes so that no answer is longer than it; a host answers at most 40 questions a second (a burst of 20) and reads at most 64 packets per poll, so a flood is dropped by the system, not worked through.
- **The nonce.** The searcher picks a random number and takes only answers that carry it back, so unsolicited packets, junk and answers to somebody else's question never reach the list. It is not security: anyone who can see the question can forge the answer (everything is plain text on the LAN).
- **The address comes from the packet**, never from the host's own claim. The Unity package's lobby carried a `HostAddress` that the host guessed with `GetLocalIP`; a phone with Wi-Fi, a hotspot and mobile data can guess wrong, and the address a packet arrived from cannot.
- **The lobbies** (`NetLobbies`, up to 16): a lobby is told apart by its game port plus **either** the address it answered from (a host that restarts keeps its place) **or** its host id (a host that answers from two of its addresses, say Wi-Fi and hotspot, is one lobby, listed at the address first heard). `NetLobbies_Update` says NEW, CHANGED (name, player count, host id or version differ), SAME or IGNORED (table full). A host of another protocol version is kept and marked incompatible, so a player can be told to update; **a host whose transport this build cannot speak** (`NetDisc_TransportSupported`: plain UDP where there is UDP, QUIC only in a build with `TOWER_MIDNET`) is kept and marked `transportSupported = false`, so a build without QUIC says "needs QUIC" instead of trying and failing. A host changing transport is CHANGED. `NetLobbies_FirstJoinable` skips full, incompatible and unsupported-transport ones. They are listed in the order they were first heard, even when a newer lobby takes an older one's freed place.
- **Addresses.** `NetDisc_DirectedBroadcast(ip, mask)` is `ip | ~mask` (192.168.1.37/24 gives 192.168.1.255: on Android the limited broadcast address often leaves by one interface only, so the directed ones are sent too). `NetDisc_IsHotspotRange` knows the subnets phones give their own hotspot or Wi-Fi Direct: 192.168.43.x (Android), 192.168.49.x, 172.20.10.x (iOS), 192.168.137.x (Windows). `NetDisc_RankHostAddresses` lists the addresses a host can tell people, best first: ordinary Wi-Fi or Ethernet, then hotspot ranges; interfaces that are down, the loopback, mobile data (`rmnet`, `ccmni`, `clat`), tunnels and 169.254.x.x (no DHCP answered) are left out. `tower_server` prints them, which is what a **browser player** types (a browser cannot search). `NetDisc_ListInterfaces` reads the machine's interfaces with `getifaddrs` (Android API 24 and up; the build targets 29).
- **The host** (`NetDiscHost`): `Open` binds the question port (0 picks a free one) with **no address reuse**, so a second host on the same machine fails to open instead of silently sharing the port and answering twice; `SetInfo` says what to announce (the name is made safe, the numbers clamped, and the transport) and is called again when the player count changes; `Poll` answers what has come in. A host that was never given `SetInfo` answers nobody.
- **The searcher** (`NetDiscClient`): `Open` takes any free port, so a searcher and a host can run on the same machine; `Search` asks (the first call always, then every 2 s); `Probe(ip, port)` asks one address directly, which works across subnets and where broadcasts are filtered; `Poll` takes the answers and drops the quiet lobbies. A send that fails on one destination (a network with no broadcast route) is ignored.

**Taken from the Unity package, changed, and left.**
- *Taken:* ask-and-answer discovery by UDP broadcast, the 2 s and 5 s timings, port 7778 beside 7777, the directed-broadcast-per-interface idea, the hotspot subnets and the order of preference for the address to show.
- *Changed:* binary packets with strict decoding instead of JSON; a padded question and a rate limit; the nonce; the address from the packet; lobby identity by host id as well; **a changed player count is reported** (the package announced a lobby only when its key was new); the Windows hotspot subnet counts everywhere (the package's `GetLocalIP` did not, its monitor did); a mobile-data address is never offered (the package falls back to any non-loopback address, which on a phone can be a carrier address nobody can reach); no address reuse on the host's port (the package sets it on both sockets).
- *Left:* Unity Netcode for GameObjects, the lobby RPCs (they trust a client-supplied id; here the server is authoritative), bots, teams. And **the package's periodic broadcast from the host**: it goes to port 7778, where only the host's own socket listens (the searcher's socket takes a random port), so it never reached any other device; only the ask-and-answer path finds a host. The Java call that asks whether a hotspot is on (`isWifiApEnabled`) is not needed either: the server just prints no address if none is usable.

**Limits.** Same network only: a broadcast crosses no router, and Wi-Fi with *client isolation* (hotel and guest networks, some routers) stops devices talking to each other at all, so neither discovery nor play can work there; `--probe` reaches a known host on another subnet but not through isolation. Everything is plain text: anyone on the network can announce a lobby or read the names. Android may drop broadcast packets while the screen is off or the radio is saving power (devices differ; unverified). A phone needs the INTERNET permission, which the manifest now declares.

### `net_mid.h` and `net_mid.c`
**What it does:** mid-net's native transport under the game's `NetTransport` seam. The owner's engine (`mid-engine`, crates under `crates/mid-net`) has a QUIC/WebTransport transport; the game is C, so a new crate there, `mid-net-transport-quinn-ffi`, puts a C interface over it (a server that binds and accepts, a client that connects, and per connection: datagrams and reliable messages), and `net_mid.c` wraps that in the same `Listen / Accept / Connect / Pump / Close` shape as `net_udp.h`. A server or a bot picks one transport or the other (`--transport udp|quic`) and nothing above it changes: `NetServer`, `NetClient` and the protocol run on QUIC exactly as they ran on UDP.

- **Where the code is.** The Rust crate and its C header live in the mid-engine repository (`crates/mid-net/transport-quinn-ffi/`, header `smoke-test/mid_net_quic.h`), which is the source of truth, so the owner can improve it there as the game goes. `src/net/mid_net_quic.h` is a **copy** of that header (declarations only: it compiles without the Rust library); when the header changes in mid-engine, copy it here again.
- **The build option.** `TOWER_MIDNET` (`platform.h`; a build option, not a platform capability): off unless the build passes `-DTOWER_MIDNET=1`, and refused with an `#error` on the web. Off, every `NetMid*` function exists and says no, so the rest of the game never needs `#if`. `bash scripts/build_server.sh --quic [outdir]` builds the Rust library with cargo (from `$MID_ENGINE`, `./mid-engine`, `../mid-engine`, or a fresh clone of github.com/Mid-D-Man/mid-engine into `<outdir>/mid-engine`; `MIDNET_CRYPTO=ring` selects the other crypto backend) and links it. Then `tower_server` and `tower_bot` speak QUIC by default.
- **A connection that is still connecting is usable.** `NetMidHost_Connect` returns at once; a reliable message sent meanwhile (the `Hello`) waits in a small outbox (8 messages) and goes out when the handshake is through; a datagram sent meanwhile is dropped, as any datagram may be. A message sent on a closed connection is refused.
- **Reliable messages ride stream 0.** QUIC delivers them whole, in order, once, so nothing of `net_reliable.c` is under this transport. The size limit stays `NET_REL_MAX_MSG` (512). A datagram is at most `NET_MTU`. Closing a transport lets queued messages (a last `Disconnect`) go out for 500 ms before the session is closed.
- **What differs from plain UDP.** QUIC encrypts the connection. `--loss` (the loss injector) applies to plain UDP only and is ignored on QUIC. The connection knows at once when the peer closes it (`NetMid_TransportState`), but the server does not use that yet: it still drops a silent client after 5 s. **`NetClient.rttMs` is the time from `Hello` to `Welcome`, measured once at connect:** over QUIC it includes the QUIC handshake (about 35 to 45 ms on the loopback where plain UDP says 1), so it is not a steady round trip; the lead that follows settles at the same 4 to 5 ticks.
- **The server is not authenticated.** The client does not check the server's certificate (the `dangerous()` pattern mid-engine's `headless-server` example uses): the connection is encrypted but a machine in the middle of a LAN could pose as the server. Pinned certificate hashes are the next step (the host could announce its hash in discovery).
- **IPv4 only on purpose.** `web-transport-quinn`'s own client binds an IPv6 socket and panics where there is none; the crate binds IPv4 itself.
- **Measured here (first time the transport could be built at all):** with rustc 1.99.1 from conda-forge the Rust side builds in this sandbox, mid-net's existing 60 unit tests pass as in the owner's CI, and the new crate's 14 integration tests and 23-check C smoke test pass over real QUIC on the loopback, with both `aws-lc-rs` and `ring`. The release `libmid_net_quic.so` is 5.3 MB on x86_64.

### The server program (`src/server/`, `scripts/build_server.sh`)
`tower_server [--port 7777] [--seed N] [--floor N] [--max-seconds N] [--loss PERCENT] [--quiet] [--name TEXT] [--discovery-port N] [--no-discovery] [--transport udp|quic]`: one floor, up to four players, the loop of this document (accept, poll, tick at 30 Hz, a status line every 5 seconds), a summary line when it stops (Ctrl-C, or after `--max-seconds`), exit code 2 if it cannot listen. `tower_bot [host] [port] [--seconds N] [--name steve] [--loss PERCENT]` (or `tower_bot --find` / `--list`, below; `--transport udp|quic` too; with `--find` the transport is the lobby's): a player with no screen that walks a fixed course and says how it went; exit 0 only if it was playing at the end, ran about the right number of ticks, and was never put back from scratch. **`bash scripts/build_server.sh` builds both** with the machine's `cc` (plain C, no raylib library, no window, `-O2` always: the player controller needs the optimiser for raymath's inline functions): `build/tower_server` and `build/tower_bot`. Their `main()` sits inside `TOWER_SERVER_MAIN` and `TOWER_BOT_MAIN`, because mray and the Android build compile every `.c` file and the game has a `main()` of its own. **No props yet** (see Known limits).

**Finding a server without typing its address.** The server prints the addresses it can be reached at (`address: 192.168.1.23:7777`, best first) and, unless `--no-discovery`, announces itself on UDP 7778 (`--discovery-port` changes it, 0 picks a free one; if the port is taken it says discovery is off and carries on; `--name` is what players see). `tower_bot --find [--wait 5]` looks for a game for up to `--wait` seconds, prints what answered and **joins the first one that can be joined**; `--list` only lists (exit 0 if anything answered); `--probe IP` asks one address directly (another subnet, or where broadcasts are filtered); `--discovery-port` must match. Exit code 3: nothing found, or nothing joinable (full, or another version of the game). `--find` with a host and port is refused (exit 2).

### `net_loopback.h` and `net_loopback.c`
A pretend link between two ends with time that only moves when the test says so. Per direction: latency, jitter (which reorders), loss, doubling. The reliable channel never loses and keeps order (a late message holds up the ones behind). A blackout loses datagrams and holds reliable messages until it ends. Datagrams over the limit are refused.

### `net_move_sim.h` and `net_move_sim.c`
`NetSim_Step` is the movement of `GameSim_Step` (`src/sim/game_sim.c`, which was `SimTick` in `main.c`: slide, sprint, `PlayerStep`, jump, in that order) from a `NetCmd`; `NetSim_Capture` and `NetSim_Apply` take and put back the movement state; `NetSim_Error` says how far apart two are (position, plus anything that would make the sprint differ a second later). **It is what `GameSim_Step` replaces once the simulation handles several players** (`sim.md`, "For multiplayer"): the single-player `GameSim` now exists and is proved equal to the old `SimTick`, but it is not on the wire yet.

### `net_server.h` and `net_server.c`, `net_client.h` and `net_client.c`
As above.

## Tests: `tests/net_headless.c`

97 checks, each with its reason in its name: the wire; the protocol (round trips to the same bytes, every refusal, command rounding, the fuzz); the pretend network (latency, 20% loss gives about a fifth lost, doubling, reordering, reliable in order, blackouts, same seed same network); the handshake (ids, the same floor on both ends, versions both ways, a full server); **prediction with no delay** (no correction after the start, the client's record of every tick within a ten-thousandth of a metre of the server's, and proof that the script really jumps, sprints and slides on the server); **a bad network** (100 ms round trip, 5% loss: no command missing at its tick, no correction); **a very bad one** (200 ms, 20% loss, 5% doubled: 0.2% missing, no restart from scratch); **reconciliation** (a shove the client could not know about is corrected and the client agrees again; the drawn player glides while the predicted one jumps; a 6 m shove is not glided; a stamina-only difference is corrected); **commands not to be trusted** (before Hello, from the far future, ten copies, late, forged full speed, a flood, junk); **other players** (within 2 cm of the truth at the time shown under 5% loss and jitter, no jumps, held in a half-second blackout, accurate again after it); **leaving and going quiet** (goodbye, a freed slot, a client that goes silent stops where it is and is dropped after 5 s, a client that hears nothing closes); **the clock lead** (adapts both ways).

**Mutation tests (36).** Each rule was broken on purpose and the tests had to fail: every wire check; every decode refusal; no loss, no order, no blackout, no size limit in the pretend network; every server rule (version, late, far future, doubled, flood limit, Hello first, repeat for ever, timeout, **a connection that never says Hello**, margin sign, run before the first command); and on the client never correcting, correcting without replaying, no smoothing, glide over a huge jump, no clock adjustment, no repeated commands, no interpolation, no 100 ms delay, a stamina difference not noticed, and the server ignoring jump or sprint. **Four survived at first and were fixed in the tests:** the server ignoring jumps or sprint (both ends share the movement code, so breaking it on both keeps them in agreement; the tests now prove the script jumps, sprints and slides), and a stamina difference (a big one also changes the speed and so shows up as a position error; a 5-point one isolates the rule).

## Tests: the reliable layer, the real network, the programs

### `tests/net_rel_headless.c` (28 checks)
Both ends of the reliable layer joined by the pretend network. A clean path (200 messages, no resends, the round trip measured right); **a path that loses 30%, doubles 10% and reorders** (500 messages in order, once each; both ends sending at once, 300 each way); **sequence numbers going round** (70,000 messages); one lost message among several (only it is sent again, the rest held back until it arrives); the window (exactly 32 taken, one byte over the size limit or none refused, a message too big for the reader's buffer dropped not cut); a receiver that does not read (the sender stops at two windows, and everything arrives in order once it reads); a dead path (given up on after a bounded number of resends, not at once); packets that are not its own (an old copy, a false acknowledgement even with messages in flight, empty, unknown, short, wrongly sized, 200,000 random). **Mutation tests (13)**, each caught: an old copy delivered again, selective acknowledgements ignored, no round-trip measure, no window limit, a dead path never noticed, sequence numbers that do not wrap, a false acknowledgement believed, an oversize message copied, a short acknowledgement accepted, a message beyond the window stored, nothing ever resent, no cap on the wait. **One survived at first**: a false acknowledgement is undone by the catch-up loop when nothing is in flight, so the test now has three messages in flight.

### `tests/net_udp_headless.c` (34 checks, about 15 seconds in real time)
A server and clients in one process over **real UDP on 127.0.0.1**. The transport by itself (a port of its own choosing; a second server cannot take it; a connection opens only on the first reliable message and is announced once; reliable and datagram both ways; size limits; **100 datagrams at an unread connection keep 32 and count the rest**). A server and two clients for a few seconds (playing within a second, 0.4 ms round trip, 144 ticks in 4.8 s, no corrections, no restarts). **15% of every packet lost and 5% doubled**, both ways: Hello and Welcome still get through, play goes on, 0 of 121 commands missing at their tick. A full server (a fifth client is told, reliably, over UDP); goodbye and the connection freed; **a stranger's junk** (200 random packets and two that are not a connection: counted, thrown away, nothing opened); **a stranger using a live connection's id from another address**; a reliable packet that is not a first one; sixteen strangers each opening a connection (no more than the slots, nobody in the game); and a client with nobody to answer (gives up after five seconds, says why). **Mutation tests (6)**: any reliable packet opening a connection, the address not checked, no limit on a connection's queue, a connection announced again and again, two servers sharing a port, and a connection that never says Hello keeping its place; all caught (the last by `net_headless.c`, where that rule is tested).

### `tests/server_smoke_quic.sh` (about 17 seconds once built; the first build compiles quinn and rustls)
The same as the smoke test above, over mid-net's QUIC: builds the server and bot with `--quic`, runs one server with two bots playing 5 s each and a third bot that lists the server (the lobby must say QUIC) and then finds and joins it with no address (three players at once, 0 corrections each), and checks that once the server is gone nothing is found (exit 3). **It needs cargo and a mid-engine checkout** (`MID_ENGINE`, `./mid-engine` or `../mid-engine`); without them it exits 77 and `run_tests.sh` reports SKIP, so a machine with only a C compiler still passes.

### `tests/net_discovery_headless.c` (116 checks, about a second)
No window, real UDP on this machine's loopback for the second half. **The packets:** a question is exactly 64 bytes; a longer or shorter one, a non-zero byte in the padding, the wrong magic, version or kind are refused; an answer round-trips field for field, the longest answer is no longer than a question, and an empty, over-long, control-character or non-ASCII name, port 0, no places, more places than the game has, more players than places and a name with no end inside its field are not sent (the last one is checked on a heap block with no zero byte anywhere, so a sanitizer sees an over-read); every cut and every flipped bit of a good answer is refused or still encodes to the same bytes; 300,000 random and spoilt packets. **The lobbies:** NEW, SAME and CHANGED (player count, name, restarted host); the same port at another address and another port at the same address are other lobbies; **one host answering from two addresses is one lobby**; another version is kept but not joinable; a full lobby is skipped; the order is the order of first hearing, also when a freed place is reused; expiry at exactly 5 s and not before; a full table ignores more and nothing is overwritten. **Addresses:** directed broadcast for /24, /28, /16 and /30, the hotspot subnets and their neighbours, which interface names can carry a game, the ranking of addresses (Wi-Fi before hotspot, mobile data, loopback, down and 169.254 left out), writing and reading dotted addresses (with the things that must be refused). **Real UDP:** a host takes a free port and a second host cannot take it; a searcher finds it with its name, game port, places and the address it *answered from*; a joining player changes 1 to 3 of 4 in the next round; junk, a short question, dirty padding, an answer and an empty packet are all unanswered and counted; a proper question from a stranger is answered with its own nonce in no more bytes; an answer to somebody else's question never gets on the list; 200 questions in an instant get a burst of answers and the rest are throttled, and later the host answers again; a probe goes straight to an address; a host that stops answering disappears after the timeout; closing frees the port; a host that was never set up answers nobody; names are made safe. Fifty-two deliberate breakages (the transport byte and its rules included): 47 were caught by the test, one (the encoder's bounds check) is caught by the sanitizer build, and four cannot be seen from outside (a 65-byte question that still fails on its leftover byte, an empty name that still fails the name check, an unset host whose answer still fails to encode, a probe to port 0 that still fails in `sendto`: each is a second line of defence). Under AddressSanitizer and UndefinedBehaviorSanitizer the test runs with no finding, and with the encoder's bounds check removed it fails there (heap overflow). The first sweep also showed three gaps that were then closed: the decoder's port 0 and place-count checks were only tested through the encoder, and the order of lobbies was only tested with lobbies added in array order.

### `tests/server_smoke.sh` (about 15 seconds)
Builds `tower_server` and `tower_bot` with `scripts/build_server.sh` and runs them **as separate programs**: one server, two bots, **10% of every packet lost on the way out**. Passes when both bots finish playing (exit 0: playing at the end, about 30 ticks a second, no restart) and the server saw both players. (5 s each: 149 ticks, 0 corrections.) Alongside the play a second server announces itself on a free port; a third bot **lists** it, then **finds and joins it with no address given** (3 s of play, 0 corrections), and once that server is gone a bot finds nothing and exits 3.

The whole suite, with the real-time tests, takes about 90 seconds. Under AddressSanitizer and UndefinedBehaviorSanitizer all of `net_headless`, `net_rel_headless`, `net_udp_headless` and `net_discovery_headless` ran with no finding.

## Not verified

- **Cross-machine determinism.** Prediction matched to a ten-thousandth of a metre because client and server ran the same binary on one machine. A phone (ARM) and a server (x86 or ARM) may differ in the last bits of a float (fused multiply-add, the maths library). The 2 cm tolerance and the reconciliation are built for that, but how often they fire between real devices is unknown until a phone talks to a server.
- **Only the loopback address.** The real-UDP tests and the smoke test ran on this machine's `127.0.0.1`, where there is no loss, delay or reordering of its own (the loss in them is injected). What a real Wi-Fi does (reordering, bursts of loss, a phone that sleeps its radio), and a second device, are untried. Frame pacing on a phone (a frame that takes 100 ms, the app in the background) is not tested either; the client runs at most 5 ticks in one update and drops the rest.
- **Termux and Android.** The server and bot are plain C99 and POSIX sockets and should build with Termux's `clang` through `scripts/build_server.sh`; nobody has tried. The Android game build compiles the transport and the manifest declares INTERNET, but nothing in the game calls the network yet.
- **Discovery has only run on the loopback.** The ask-and-answer path, the lobby table and the interface list were tested on this machine; a real Wi-Fi was not. Open questions: whether a given phone sends and receives broadcast packets on its Wi-Fi and its hotspot (and with the screen off), whether the directed broadcast of an Android hotspot's interface works, and how a router with client isolation behaves (it should simply find nothing). The sandbox has a single test-network address (192.0.2.2), so the ranking of a real phone's interfaces (`wlan0`, `swlan0`, `rmnet_data0`) is tested with made-up lists, not with a phone's. **The first real try is the lobby's FIND GAMES** (`lobby.md`, which lists what discovery finds and runs on the phone, with the INTERNET permission now in the manifest): run `tower_server` on one device on the same Wi-Fi or hotspot and open FIND GAMES on the other.
- **The browser's WebTransport is not connected, and native QUIC in the APK has not run on a phone yet**: `net_mid` works in the server and bot programs built with `--quic` (here, and in Termux if cargo is there); the Android build script builds the Rust library for armv7 (built on GitHub) and links it, but the link into the APK and a run on a phone have not been seen yet (`android.md`); see "what comes next".
- Nothing here has been run in the game or on a screen.

## Known limits (what this slice is not)

- **Movement only.** Shots, hits, enemies, the swarm, doors, stairs, the stair clock, pickups, the inventory, the flashlight and health are in `GameSim` now (`sim.md`) but not in the netcode: the netcode still runs `NetSim_Step`, the movement alone. Putting them on the wire needs `GameSim` to take several players (`sim.md`, "For multiplayer") and the monsters, projectiles and pickups, which are module-global (so one simulation per process), in the snapshots.
- **Props.** The player's movement collides with the floor's props (`CheckObstacleCollision`, a module-global list). The tests have no props. Today the props are one fixed crate that `InitObstaclesSystem()` places the same way on every floor (`sim.md`), so a real server and client only both have to call it; when props depend on the floor they will need its seed, and until then prediction is wrong within reach of that crate if one side lacks it.
- **`NetCmd` is out of buttons.** Its `buttons` field is one byte and all eight bits are used (sprint, USE held, jump, fire, use, swap, light, slide). The simulation's command now has ten flags: it also takes **reload** and **dive** presses (`SimCmd`), which have no bit. The field has to be widened to 16 bits (a change to `NetCmd`, the wire format and its tests, with `NET_PROTOCOL_VERSION` bumped) before the simulation goes on the wire; it costs 4 bytes per input packet (each carries four commands). **Reload is only the owner's business:** the server must be told when a player reloads (it owns their ammunition), so the bit travels in that player's own command, but the snapshots to other players never carry it, because other players do not need to see a reload (the owner's decision).
- One floor per server; changing floors is not handled. Players do not collide with one another and all start at the same place. No health or death in the netcode yet.
- Snapshots are whole every tick: no deltas, no interest management, 4 players at most.
- The client's aim is trusted as sent (fine for co-op, not for a competitive mode).
- A returning network after a gap shows the other player jumping to where they now are (they did move); there is no catch-up glide and no extrapolation.
- Only the physical movement state is compared when reconciling; the camera's eye height and head bob are not.
- **No encryption and no sign-in on the UDP transport**: everything is plain text, and the connection id is a random number, not a secret (anyone on the path who sees one can learn it; the address check stops a casual stranger, not someone who can also forge the address). Fine for a LAN and for trying things, not for the open internet. QUIC (`net_mid`) encrypts, though it does not yet check who the server is (see `net_mid.h`); a sign-in is for the lobby.
- **No reach beyond the local network by itself**: a server on a phone behind mobile data (carrier NAT) cannot be reached; same Wi-Fi works, and a machine with an open UDP port works. IPv4 only. No keep-alive packet: a connection is kept alive by the 30 Hz of play, and a client sitting in a menu would be dropped after five seconds of silence.
- A UDP connection is freed only when the game closes it; a game that never does leaks the slot (the server always does).

## What comes next

1. **Several players in `GameSim`.** The single-player simulation has been moved out of `main.c` (commands in, events out, replay test at several frame rates, proved identical to the old code: `sim.md`). Next: an array of players (nearest-target selection for monsters and the swarm, per-player arsenal, inventory, flashlight, health, events), yaw and pitch in the command, then `NetSim_Step` is replaced by `GameSim_Step` and the snapshots grow. `SimCmd`'s fire press maps to `NetCmd`'s FIRE bit as it is (`sim.md`).
2. **The client in the game**: a menu to host or join (the host runs the server program, or the game starts the server loop itself; the join list is `NetDiscClient`'s lobbies, with a typed address for the browser), `NetClient_Update` in the frame loop, the other players drawn.
3. **A real-network trial**, which needs no game change any more: `bash scripts/build_server.sh` on both devices, `build/tower_server` on one and `build/tower_bot --list` then `--find` on the other, over the owner's Wi-Fi (or one phone's hotspot); the first time the numbers in "Not verified" get tested (cross-device determinism, reordering, the phone).
4. **mid-net in the Android build and in the browser.** Android: **the cross-compile has built on GitHub; the final link and a run on a phone are not seen yet**: `scripts/build_android.sh` builds the Rust library for armv7 with cargo and the NDK's clang (ring, pinned by `android/midnet.Cargo.lock`) and links it with `-DTOWER_MIDNET=1`, and the `Android APK` workflow checks mid-engine out and caches the build (`android.md`); the `Android APK` run's summary page says whether the library made it into the APK. Browser: WebTransport through mid-net's wasm transport (a separate wasm module reached from the Emscripten build), or a WebSocket dev transport; the owner has not chosen. Both need the certificate question settled (pinned hashes).

## Fixes and Problems

- **The player controller needs the props function.** Linking it for the first time here failed on `CheckObstacleCollision`; the test supplies "no props" as the movement tests do.
- **A test measured the wrong thing.** The reconciliation test shoved the player 1.7 m, which became 2.4 m once the commands since were run again, over the client's two-metre "do not glide" limit, so it saw no glide. Now a 1 m shove tests the glide and a 6 m one tests the snap.
- **The half-second blackout test's window included the moment the network came back**, so it saw the (correct) jump to where the other player now was. The window ends before that, and a second check says they are accurate again afterwards.
- **The slide never happened in the first script** (a wall stopped the sprint, and a slide needs 2 m/s); found only because a test counted slides. The script now tries more than once.
- A statically allocated pool of link ends was replaced by two ends inside each link before it could bite a test that makes many links.
- **Junk could open a connection.** The first real-UDP test of a stranger's packets failed: about 1 in 256 random packets has the reliable-data kind byte, and the server made a connection for any such packet, which then held a player place for up to five seconds. Now a connection opens only for the first reliable message of one (sequence number 0), and a connection that has not said Hello in 3 seconds is dropped.
- **One host was listed twice (found by the discovery test).** A host reached through two of its addresses (here the loopback and the machine's own interface) answered each question twice from two source addresses, and a table keyed by source address alone listed two lobbies. A phone with Wi-Fi and a hotspot would do the same. A lobby is now also recognised by its host id, and the address first heard is kept.
- **The encoder read a name past its field.** `NetDisc_EncodeAnnounce` took the length of the name with `strlen` on a field that might have no end. Now it looks for the end inside the field first. The first test of it passed anyway, because the one byte of padding after the name happened to be zero; a heap block with no zero byte anywhere is what makes a sanitizer build fail on the unguarded code.
- **A test had three different hosts with one host id** and so, rightly, saw one lobby; the hosts now have their own ids. Two timestamps in the expiry test were simply wrong (3,700 ms is not more than 5,000).
- **A resend wait that grew to four seconds** made a dead path take 36 s to notice (and a handshake over a lossy link slow); it is now capped at one second (about 11 s to give up).
- **`SO_REUSEADDR` removed**: on UDP it would have let a second server silently share the first one's port. The test that tries it crashed under the mutation, which is how it was confirmed to matter.
- Two tests were wrong rather than the code: one expected a receiver that never reads to stop the sender at one window (it is two), and one stopped the instant the last message arrived, before its acknowledgement could.
