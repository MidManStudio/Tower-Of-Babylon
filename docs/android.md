# android

## Overview

The Android build turns the same C99 + raylib source that mray compiles for the browser into a sideloadable APK for 32-bit ARM (`armeabi-v7a`, the only ABI the Galaxy A13 installs; the sister project Terminal Viscosity established that). It is built by GitHub Actions, so nothing is needed on the phone beyond a browser: open the Actions tab, run **Android APK**, download the artifact (a zip with one `.apk` inside), unzip, install.

The pipeline is six stages in `scripts/build_android.sh`: build raylib 6.0 from source for Android; **build mid-engine's QUIC library (Rust) for armv7**; bake `assets/config/*.mdix` into `src/config/config_baked.c`; compile `main.c` and every `src/**/*.c` with the NDK (with `-DTOWER_MIDNET=1` when the library exists); link them with raylib and the QUIC library into `libmain.so`; package, align and sign the APK. The QUIC library is mid-net's native transport (`src/net/net_mid.c`, `docs/net.md`). Nothing in the game calls the network yet, so the APK carries it but does not use it; the point of having it in is that the first menu that hosts or joins a game can use it without the build changing. There is no Java code (`android:hasCode="false"`): the activity is Android's `NativeActivity`, which loads `libmain.so`, and raylib's `android_main` calls the game's own `main()`.

## What is the same and what is different from the browser build

- The game is drawn at 800 x 450 and raylib scales it. raylib 6.0's Android backend keeps `GetScreenWidth()` at 800 and `GetScreenHeight()` at 450, makes the render buffer the shape of the real screen, centres the 800 x 450 picture with black bars (a 20:9 phone is wider than 16:9, so the bars are at the sides) and maps every touch back into 800 x 450 (`rcore_android.c`, `SetupFramebuffer` and the touch code, read in the 6.0 source). So the HUD rectangles and touch zones in `main.c` work unchanged.
- OpenGL ES 2.0 is the graphics API in both. `src/ui/view_clip.c` (the depth clear between world and hands, the depth and MSAA readout) and `src/ui/highp_shader.c` (the highp program and the flashlight beam program) used to run only in the browser; they now run wherever the platform has the capability `TOWER_GLES2` (web and Android, see `platforms.md`). Without that the hands would be drawn without a depth clear and there would be no beam. See `docs/lighting.md`.
- Config comes from the baked copy only. The DixScript wasm is a browser thing (`src/config/mdix_web.c` says "no" off the web, which the diagnostics overlay shows as `config: baked copy (wasm off)` with an orange note; that is expected on Android). The bake stage makes sure the baked copy matches the `.mdix` files in the checkout.
- Files are opened as `assets/config/...`, `assets/shaders/...` exactly as in the code. raylib on Android reads them from the APK's asset folder, so the project's `assets/` goes into the APK as `assets/assets/`. `assets/mdix/` (the 3.5 MB browser wasm) is left out.
- Audio is the same code. raylib's Android build carries its sound backend (`-lOpenSLES` is already in the link line), and `Audio_Update` opens the sound card on the first frame instead of waiting for a touch (that wait is the browser's rule: the capability `TOWER_AUDIO_GESTURE_UNLOCK`, see `platforms.md`). The limiter, the loops and the tap-to-audition line in the diagnostics work as in the browser. Not heard on a device yet; see `docs/audio.md`.

## Modules

### `scripts/build_android.sh`
**What it does:** the six stages above (`raylib midnet bake compile link package`). `bash scripts/build_android.sh` runs all of them; `bash scripts/build_android.sh compile link package` runs some (the raylib stage is the slow one and its checkout stays in `build/android/raylib`; the compile and link stages find the QUIC library the midnet stage left in `build/android/midnet/`, so they can be run alone). Settings by environment: `TOWER_ANDROID_API` (29), `TOWER_ANDROID_TARGET_SDK` (34), `TOWER_ANDROID_BUILD_TOOLS` (34.0.0), `TOWER_ANDROID_PLATFORM` (34), `TOWER_RAYLIB_TAG` (6.0), `TOWER_OPT` (-O2), `TOWER_VERSION_CODE`, `TOWER_VERSION_NAME`, and for the QUIC library `TOWER_MIDNET` (1; 0 = never build or link it), `TOWER_MIDNET_REQUIRED` (0), `TOWER_MIDNET_CRYPTO` (`ring`, or `aws-lc-rs`), `TOWER_MIDENGINE_REF` (a branch or tag to clone; default: the default branch), `MID_ENGINE` (a path to a mid-engine checkout). It writes a short report to the run's summary page when it runs on GitHub (`GITHUB_STEP_SUMMARY`) and puts warnings on the run page as annotations.

**Decisions:**
- raylib is built from source at tag 6.0, and the game compiles against the headers of **that** checkout (`-I build/android/raylib/src`), not against `raylib/src/` of the project, whose `libraylib.a` is the web build and whose headers are 6.1-dev. The library and the headers therefore always agree. All 36 game sources were compiled on the host against the 6.0 headers with no error and no implicit declaration, so 6.0 has every function the game calls. `-Werror=implicit-function-declaration` keeps that true: a raylib call that a future raylib lacks fails at compile time with its name, not at the link.
- The raylib build line, the link flags and the library list (`-llog -landroid -lEGL -lGLESv2 -lOpenSLES -lm -ldl -lc`, `-u ANativeActivity_onCreate`, `-Wl,--wrap=fopen`) are the ones Terminal Viscosity's `scripts/build_android.sh` uses, which is known to run on the phone. `--wrap=fopen` is required by raylib's Android file loading; `--no-undefined` turns a missing symbol into a link error.
- `-std=gnu99` rather than `-std=c99`: the tests build the code with strict `-std=c99`, so it is plain C99; gnu99 only avoids surprises in bionic's headers.
- The bake stage runs `node tools/mdix_bake.mjs` and then `--check`. It rewrites `src/config/config_baked.c` in the CI checkout (not committed), so a `.mdix` edit that was never baked still reaches the APK.
- **The midnet stage** builds `crates/mid-net/transport-quinn-ffi` of mid-engine (public: `github.com/Mid-D-Man/mid-engine`) with `cargo rustc -p mid-net-transport-quinn-ffi --lib --crate-type staticlib --release --target armv7-linux-androideabi`: only the static library, so no `cdylib` has to be linked. The NDK's `armv7a-linux-androideabi29-clang` is given to cargo and to the `cc` crate through `CC_armv7_linux_androideabi`, `AR_armv7_linux_androideabi` (llvm-ar) and `CARGO_TARGET_ARMV7_LINUX_ANDROIDEABI_LINKER`, which is what cargo-ndk would do, so cargo-ndk is not needed. mid-engine is looked for in `MID_ENGINE`, `./mid-engine`, `../mid-engine` and `build/android/mid-engine`, and cloned (depth 1) from GitHub when none has it; the workflow checks it out into `./mid-engine`.
- **`ring` is the crypto backend on Android**, not `aws-lc-rs` (mid-engine's default). aws-lc-sys wants cmake and its own Android handling; ring needs only the C compiler the NDK gives. `TOWER_MIDNET_CRYPTO=aws-lc-rs` tries the other (not tried). Both are TLS backends for QUIC; the game's protocol is the same on either.
- **Rust is asked from inside the mid-engine checkout.** Its `rust-toolchain.toml` says `stable`, and rustup picks the toolchain by folder, so the version printout, the check for the installed `armv7-linux-androideabi` target and `rustup target add` all run there.
- **`android/midnet.Cargo.lock` pins the dependency versions.** mid-engine commits no `Cargo.lock`, so without one every run would take the newest version of ~520 crates, and a new release could break an Android build that worked yesterday. The file is the lock cargo made when the library was built and tested here (rustc 1.99.1, `ring`); the script puts it in the mid-engine checkout for the build and removes it again (a checkout that has its own `Cargo.lock` keeps it). When mid-engine's dependencies change a lot, refresh it: build once without it, copy the `Cargo.lock` cargo made to `android/midnet.Cargo.lock`.
- **Where an error cannot hurt the APK:** the midnet stage runs in a child process (`bash build_android.sh midnet_inner`, an internal stage name), the checks after the build ignore the exit status of tools that may be older than the compiler's LLVM, and `set -E` with an `ERR` trap makes any stop name its command and line.
- **If the library cannot be built, the APK is built without it, loudly** (a warning in the log and on the run page, "QUIC in it: no" in the summary; since round 8 that APK also has **no multiplayer at all**, because every connection goes through the driver that is in the same library, and the warning says so): no cargo, no target, no mid-engine, a cargo error (its output is in `build/android/midnet.log`), a function that `src/net/mid_net_quic.h` or `src/net/mid_net_driver.h` declares but the library lacks (the headers are copies of mid-engine's), or a **link** that fails or that pulls in a library the phone does not have (`libc++_shared.so` and `libunwind.so` are not in the APK; the reason is in `build/android/midnet-link.log`). In the last case the sources are compiled again with `-DTOWER_MIDNET=0 -DTOWER_NETDRIVER=0` and linked without the library. `TOWER_MIDNET_REQUIRED=1` turns every one of these into an error, for when a build without QUIC is not wanted. The reason for the default: nothing in the game uses QUIC yet, and a Rust problem must not stop an APK that is otherwise fine.
- **The library carries the driver (round 8).** `libmid_net_quic.a` is built from `mid-net-transport-quinn-ffi`, which now depends on the facade `mid-net` and re-exports the driver's C functions, so the game links ONE Rust library (two Rust static libraries cannot be linked together: duplicate `std`). This needs mid-engine with that change (the tarball of round 8); against an older mid-engine the symbol check above names the missing `mid_net_driver_*` functions and the APK is built without multiplayer. **`TOWER_MIDNET_REQUIRED=1` (the workflow's `require_quic`) is now the safer way to run it** while the link has not been seen: the run fails instead of giving an APK that cannot play together.
- **A library left over from an earlier run is never linked by accident**: the midnet stage deletes `build/android/midnet/libmid_net_quic.a` before it does anything else (so a failed run leaves none), and the compile and link stages ignore the file when `TOWER_MIDNET=0`.
- The package stage uses `aapt`, `zipalign` and `apksigner` the same way Terminal Viscosity does, with a throwaway debug key (`debug.keystore`, alias `towerdebug`, password `android`). It prints the badging (package, SDK, launcher activity, native code) at the end.

### `android/AndroidManifest.xml`
**What it does:** declares the app as a native activity with no Java, and asks for the `INTERNET` permission (sockets: LAN discovery and the network transports in `src/net`). Package `com.midmanstudio.towerofbabylon`, landscape, OpenGL ES 2.0 required, `@MIN_SDK@`, `@TARGET_SDK@`, `@VERSION_CODE@` and `@VERSION_NAME@` filled in by the script (defaults 29, 34, 1 and 0.1.0; the workflow passes the run number).

**Decisions:** `INTERNET` is the only permission, because it is the only one the native code needs: it is a normal permission (granted at install, no prompt). `ACCESS_WIFI_STATE`, `CHANGE_WIFI_MULTICAST_STATE` and the like are for Java calls (`WifiManager`), the app has no Java, and the native code reads the interfaces with `getifaddrs`; add them if a phone turns out to need a multicast lock. The rest is the same structure as Terminal Viscosity's manifest, which is known to install and run on the phone, with only the names changed. `android:exported="true"` is required on Android 12 and newer. `configChanges` stops the activity being recreated on rotation or resize.

### `.github/workflows/android.yml`
**What it does:** manual only (`workflow_dispatch`), with three inputs: `quic` (on/off: build the QUIC library and link it; default on), `require_quic` (on/off: fail the run when the library cannot be built or linked instead of building the APK without it; default off) and `mid_engine_ref` (a mid-engine branch, tag or commit; empty = its default branch). Steps: check out the game; check out mid-engine into `./mid-engine` (public repository, no token; `continue-on-error`); Java 17, Node 20 (for the bake), the Android SDK (platform-tools, build-tools 34.0.0, platform 34), NDK r26d; Rust (`rustup toolchain install stable --profile minimal --target armv7-linux-androideabi`, `continue-on-error`); the cache of cargo's registry and of `build/android/midnet/target`; the debug key from the Actions cache; then `scripts/build_android.sh`; then uploads the APK as `tower-of-babylon-armv7-debug-apk` and, even when the build failed, the cargo log and the link log as `midnet-build-log`. The run's summary page says whether QUIC is in the APK.

**Decisions:**
- The tool setup copies Terminal Viscosity's `android.yml`, which builds on GitHub today, minus Rust, Odin and the DixScript library, none of which this game uses.
- **The debug key is cached** (`actions/cache`, key `tower-debug-keystore-v1`). A phone only updates an installed app in place when the new APK has the same signing key; with a key regenerated on every run you would have to uninstall the old build each time. With the cache, later builds install over the old one. GitHub drops cache entries that have gone unused for 7 days, and then the next APK has a new key: uninstall the old app first (there is no save data to lose). The key is a throwaway with a public password; it protects nothing.
- `versionCode` is the run number, so each build is newer than the last.
- **The two QUIC steps may fail without stopping the run** (`continue-on-error`): the script is the one place that decides whether a missing mid-engine or Rust means "build without QUIC and warn" or "stop" (`require_quic`). The workflow only prepares what the script looks for (`MID_ENGINE` points at `./mid-engine`).
- **The Rust cache** is keyed on `android/midnet.Cargo.lock` and a hash of mid-net's sources, with the older caches as fallbacks: when mid-engine changes, the newest older cache is restored and cargo rebuilds only the crates that changed (the ~500 registry crates, which are the slow part, come from the cache). A cold build of the library is expected to take a few minutes; the job's timeout is 45 minutes.
- Unlike the other files of this repository this one is a workflow, so it is **not applied from a tarball** (dot path): it is committed by hand to `.github/workflows/android.yml` (`docs/repo.md`).

## Installing on the phone

1. Actions tab, **Android APK**, Run workflow (the defaults build with QUIC). It takes a few minutes, most of it raylib and, on a cold cache, the Rust library. When the run is done its page shows a summary: the APK, and whether QUIC is in it. A yellow warning means the APK was built without QUIC and says why.
2. Download the artifact; it is a zip, unzip it (a file manager does it).
3. Open the `.apk`. Android asks once to allow installs from that app (the file manager or the browser).
4. If it says the app conflicts with an existing package, uninstall the old Tower of Babylon first (different signing key, see above).
5. To read the game's log: `adb logcat -s raylib` over USB or wireless debugging. The lines that matter: `DISPLAY: depth buffer ... MSAA samples ...`, `SHADER: high precision shader loaded`, `SHADER: flashlight shader loaded`, and raylib's `DISPLAY: Upscaling required` with the viewport offsets.

What was run here: the same cargo command for the host (x86_64) with `ring`, which linked into a PIC shared object with `-Wl,--no-undefined -Wl,--gc-sections` together with `net_mid.o` built with `-DTOWER_MIDNET=1`, with the 12 `mid_net_quic_*` functions of the header in it; and `tests/android_script_check.sh`, which drives the script's stages against a fake NDK, cargo and rustc (53 checks; 38 deliberate breakages of the script, all caught). If the link fails, the APK is built without QUIC and the summary says so (`midnet-build-log` has the details).
- Nothing in the game calls the network, so even a successful build proves only that the library links, not that it works on the phone. The first real test is a menu that hosts or joins (see `docs/net.md`, "what comes next").
- The size of the APK with the library, and of `libmain.so`: the script prints both; the static library is 18 MB on the host before linking (the linker keeps only what is reachable from the QUIC functions).
- `aws-lc-rs` as the crypto backend on Android, and an `arm64-v8a` build of the library (the script builds one ABI).

- None of the NDK, SDK, `aapt`, `apksigner` or raylib-for-Android steps have run. The script was checked with `bash -n` and shellcheck, the workflows parse as YAML, and the C compiles on the host against the 6.0 headers (syntax and declarations only, not an ARM build). The Android-only branches in `view_clip.c` and `highp_shader.c` were syntax-checked against a stand-in `GLES2/gl2.h`.
- The first real run will show whether anything in the raylib 6.0 Android build differs from what Terminal Viscosity needs; it uses the same Makefile invocation.
- How the picture looks on the screen (the bars, the touch zones lining up with the drawn buttons), whether the highp and beam shaders compile on the Mali's driver, how fast it runs against the browser build, and whether `EGL_SAMPLES 4` (MSAA from `FLAG_MSAA_4X_HINT`) is accepted by the device. The diagnostics overlay (tap the FPS counter) and `adb logcat` answer these.
- Only `armeabi-v7a` is built. A 64-bit phone could run it too if it allows 32-bit apps; an `arm64-v8a` build would need `ANDROID_ARCH=arm64`, the `aarch64-linux-android` compiler and its own `lib/arm64-v8a/` folder, and has not been tried.

## Fixes and Problems

### `scripts/build_android.sh`
- **First CI run of the QUIC stage: cargo succeeded, then the build died with exit code 1 and no message.** The cause: after the build the script lists the symbols of `libmid_net_quic.a` with the NDK's `llvm-nm` (to check that every function `src/net/mid_net_quic.h` declares is in it). `llvm-nm` of NDK r26d is LLVM 17, the library was made by rustc 1.100 (LLVM 23), and `llvm-nm` exits 1 with "Unknown attribute kind" on 65 of the library's 340 members (the bitcode rustc embeds in objects of `compiler_builtins`), while still listing every symbol it can read (all 12 `mid_net_quic_*` functions were in the output when reproduced here with LLVM 17's `llvm-nm`). The script captured that output with `set -e` active and its error output thrown away, so the shell stopped at the first failing command and said nothing. Fixes: the exit status and the complaints of that `llvm-nm` are ignored (the complaints go to `build/android/midnet-nm.log`); an empty result skips the check with a warning; **the whole QUIC stage now runs as a child process**, so an error nobody expected costs the APK its QUIC library (warning, `QUIC in it: no`) and never the APK; and an `ERR` trap names the command and the line whenever the script is stopped (`error: build_android.sh stopped at line N: ...`). The members are ELF objects (all 340), so the final link is not affected by this: only tools that read the embedded bitcode complain.
- The QUIC link adds `-Wl,--strip-debug`: the parts of Rust's standard library that rustc ships precompiled carry debug info, and the game itself is built without `-g`, so this drops only theirs and keeps `libmain.so` from growing with it.
