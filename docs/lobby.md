# lobby

## Overview

The lobby is the first screen of the game. It shows who the player is (the chosen character), and has four buttons: **CHOOSE / CHANGE CHARACTER** (opens the character screen, `characters.md`), **PLAY SOLO** (starts the game, exactly as the game always started), **FIND GAMES** (a list of the games found on the network) and **HOST A GAME** (greyed out). It is two screens of its own, HOME and FIND, and it is the place the character screen is reached from: the character screen no longer opens by itself at launch.

**What is real and what is not.** Real: PLAY SOLO, the character button, and the list in FIND, which is the LAN discovery of `net.md` (a `tower_server` running on the same Wi-Fi or hotspot shows up in it by itself, with its name, its players and its transport). Not built: **hosting and joining.** Nothing in the game runs a server or a client yet, so HOST is a grey button that says "not yet: the game has no server in it", games in the list can be highlighted but not entered, and the screens say so in words. The screens do not pretend: a button appears only where the thing behind it exists, and a button that does not is shown off with the reason on it.

**The lobby is the first screen only.** After dying or at the end of a run the game does what it did before (see `floor_run.md`); it does not come back to the lobby yet.

## What the screens look like

800 by 450, like the character screen (cards, text and buttons in canvas pixels).

**HOME.** Top left, the title (TOWER OF BABYLON, HORROR GAME SHOW). Left, a box headed YOUR CONDEMNED: the chosen character's short name large, then the full name, the role and the overview (up to six lines), or NOBODY CHOSEN YET with "Choose who climbs the tower." when nobody is; at its foot a button, CHOOSE CHARACTER, or CHANGE CHARACTER once somebody is chosen. Right, a column of three big buttons: a green **PLAY SOLO** (off, with "CHOOSE A CHARACTER FIRST" on it, until somebody is chosen); **FIND GAMES** ("ON THIS NETWORK"); **HOST A GAME** (always off for now, "NOT YET: THE GAME HAS NO SERVER IN IT"). Under the column, a line saying whether the player is ready and a grey line saying that joining and hosting come with the in-game network.

**FIND.** Title FIND A GAME and a BACK button top right (in the same place as the character screen's). A list of up to five rows at a time, each a game: its name large, "1 / 4 PLAYERS" and the transport (UDP or QUIC) small, and, for a game that cannot be joined, the reason in red on the right (OTHER VERSION, NEEDS QUIC, CANNOT CONNECT, FULL). More than five games: UP and DOWN arrows on the right. Under the list a status line: SEARCHING THE NETWORK... (with moving dots), "2 GAMES FOUND", or why there is no list (below), then two grey lines saying what the list is and that joining is not in the game yet.

**Taps and keys.** A tap on a button that is on presses it; a tap on an off button does nothing. On FIND a tap on a row highlights it (and nothing more). Keyboard: A / D or the arrow keys step through the buttons that are on (HOME) or through BACK and the games (FIND), Enter or Space presses; the focused button is outlined in yellow while the keyboard is the control scheme in use, and a hint line names the keys. BACK on the character screen has no key, only a click or tap.

## Flow (`main.c`)

`AppScreen`: `SCREEN_LOBBY` (the first), `SCREEN_CHARACTER`, `SCREEN_GAME`. The lobby's CHOOSE CHARACTER opens the character screen with the highlight on the chosen character; CHOOSE (or BACK) there returns to the lobby; PLAY SOLO starts the game: the fixed-step clock and the command latch are reset and the game fades in, as after a door. While either screen is up none of the game runs (no steps, no monsters, no clock, no 3D). With no characters at all (`Characters_Count() == 0`) PLAY SOLO is on at once and the character button says NO CHARACTERS (off), as the game with no roster always started without a screen.

## Modules

### `lobby_backend.h`
**What it does:** the whole of what the lobby needs from the network, as a struct of function pointers (`LobbyBackend`): can a search run here (and if not, the reason in words), start a search (it may fail), stop it, update it once per frame, how many games there are, and the nth (`LobbyEntry`: name, players, maximum, transport, joinable, and a reason when not). **Decisions:** the screen never touches a socket, so the logic is tested with a backend that answers from a script, and the real one can change underneath it. Strings are plain ASCII and are copied by the lobby, so a backend may reuse its buffers.

### `lobby.h` and `lobby.c`
**What it does:** the logic and the layout of both screens, with no raylib in it. `Lobby_SetContext(rosterCount, hasChoice)` is given every frame; `Lobby_Move`, `Lobby_Press` and `Lobby_Tap` take the input; `Lobby_Update(backend, nowMs)` is where the search is started and stopped and the games copied in; `Lobby_TakeWant()` hands over once what the screen wants from the game (`LOBBY_WANT_CHARACTER`, `LOBBY_WANT_PLAY`): it neither opens the character screen nor starts the game itself.
**Decisions:**
- **The buttons that are on:** CHARACTER when there is a roster; PLAY when there is no roster or somebody is chosen (the same rule the game had: no roster, no screen); FIND always; HOST never. The focus is always on a button that is on: it moves when the one it was on goes off, and when somebody has just been chosen it jumps to PLAY (the next thing to do), once.
- **The backend is called in one place.** Taps and keys only change the screen; `Lobby_Update` compares "is FIND open" with "is a search running" and starts or stops the search to match. A search that cannot run (no backend, a browser) or fails to start is a state of its own (`LOBBY_SEARCH_UNAVAILABLE`, `LOBBY_SEARCH_FAILED`) that the screen shows in words; it is not retried every frame, only when FIND is opened again. Leaving FIND stops the search and forgets the games.
- **The games are a copy**, refreshed every frame while searching, so the backend's own table can change under the screen. At most 16 (`LOBBY_MAX_ENTRIES`, the discovery's table size) and the backend is never asked about more than that. A game the backend says is gone is left out; the others keep their order (the discovery table's order).
- **The highlight is an index, not an identity**: if the list shrinks the highlight moves to the last game; if the game it was on goes and another takes its place the highlight stays on the row. Nothing can be done with a highlighted game yet, so this costs nothing now. When joining exists it should follow the game (its address and port), not the row.
- **Scrolling:** the keyboard moves the highlight and the view follows it; the arrows on screen move the view and leave the highlight alone (a view that jumped back to the highlight would make the arrows useless).
- **BACK is where the character screen's BACK is**, so a thumb learns one place.
- **The layout** is functions returning `UiRect`s, in canvas pixels, so the tests check it without a window: the character box, the four buttons, the status box, BACK, the list, five rows, the two arrows.

### `lobby_net.h` and `lobby_net.c`
**What it does:** the real backend over `net_discovery.h`. Searching opens a `NetDiscClient` (on `NET_DISC_PORT` unless a test says otherwise, `LobbyNet_UsePort`), and each update asks when a round is due and takes the answers; the games it lists are the table of the client. `LobbyNet_EntryFromLobby` turns one into a `LobbyEntry`: joinable means a version this game speaks, a transport this build has, and room for one more; otherwise the reason, in this order: OTHER VERSION, then NEEDS QUIC (a QUIC game on a build without QUIC) or CANNOT CONNECT (a UDP game on a build without UDP), then FULL. Where there is no UDP (the browser) `canSearch` is false and the reason is "A BROWSER CANNOT SEARCH THE NETWORK. USE THE APP." **Decisions:** one static client, because one lobby needs one search; `LobbyNet_Shutdown` is safe at any time and is called when the game ends. On Android this needs the INTERNET permission, which the manifest now declares (`android.md`).

### `lobby_ui.h` and `lobby_ui.c`
**What it does:** draws both screens (`LobbyUI_Draw(lobby, showKeys)`), clearing the background itself. Plain `DrawText` and rectangles, like the HUD and the character screen, and the same word wrap (`CharSelect_Wrap`) for the character's overview. It reads the chosen character from the characters module and the games from the `Lobby` (never from the backend). No test can run it (it needs a window); it is compiled for web, Android and desktop by `tests/platform_check.sh`.

### `main.c`: `LobbyFrame`, `SelectFrame`, `BeginRun`
**What it does:** `Frame()` starts with the screen switch. `LobbyFrame` polls the config (so the real `characters.mdix` can arrive), gives the lobby its context, reads the menu and the tap, updates the lobby with the clock (`GetTime() * 1000`), keeps the audio's gesture unlock going, acts on what the lobby wants, and draws. `SelectFrame` does the same for the character screen and, when the player chose, stores the id and goes back to the lobby (BACK also goes back, storing nothing). `BeginRun` is what used to be the end of the selection screen: reset the clock and the command latch, fade in.

## Tests

### `tests/lobby_headless.c` (110 checks)
No window, no raylib calls. **HOME:** which buttons are on for each roster and choice, the focus rules (off buttons skipped, the move to PLAY after choosing and only then, the roster vanishing under the focus), the keyboard (both directions, wrap, no step), what each press and tap asks for, the want handed over once, taps on off buttons and on nothing. **The search lifecycle** against a scripted backend: not started by merely opening FIND, started once, updated with the time it is given, stopped once on leaving, started afresh on returning with no old games; a backend that cannot search (the reason shown, nothing started, nothing stopped), a missing backend, a missing reason, a search that fails to start (not retried every frame, retried on reopening), a backend that vanishes mid-search. **The list:** the copy, the ring of BACK and games, ENTER on a game doing nothing, a tap on a row and on an empty row, the games vanishing under the highlight, more games than room (and the backend not asked about more), a gone game left out. **Scrolling:** the arrows, their ends, a row tap after scrolling, the highlight untouched by the arrows, the view following the keyboard both ways, the list shrinking under the view. **Layout:** everything on the canvas, no overlaps on either screen, the buttons and rows big enough for a thumb, BACK in the same place as the character screen's. **The real backend:** every conversion and its priority of reasons, a long name, `canSearch` following the platform, the shutdown twice; and, where the platform has UDP, a real host answering on this machine through the real search: the game appears with its name, players and transport, follows the host filling up (FULL), disappears on BACK, and the search can open again.

**Mutation tests (42).** Each rule was broken on purpose and the tests had to fail: a character button on with no roster, PLAY on with no choice or off with no roster, HOST on, a focus that is not fixed, no jump to PLAY after choosing, the wrong want, a FIND that opens with the focus elsewhere, a step that lands on an off button, a ring that runs backwards, a step that does not scroll, ENTER on a game going back, rows not capped, a tap on an off button moving the focus, an arrow that does not clamp or scrolls the wrong way, a row tap that ignores the scroll, a search restarted every frame, a failed start counted as searching, a search never stopped, games kept after leaving, a count not clamped (the first test missed this one: nothing observed how many games the backend was asked about, so a check was added), a gone game kept, a focus not clamped, a reason not copied, a want not cleared, BACK in the wrong place, overlapping buttons and rows; and in the real backend a reason order changed, everything joinable, UDP and QUIC swapped, a stop that leaves the client marked open, answers never taken, questions never asked, a backend that can never search; and in the character screen (`characters.md`) a BACK that does not leave, an open that takes any focus, moving or choosing after leaving, a BACK that needs characters, a BACK over the cards.

The character screen's own new checks (BACK and opening again, 13) are in `tests/characters_headless.c`, now 75 checks.

## Not verified

- **Nothing here has been seen on a screen.** The drawing (`lobby_ui.c`) compiled for all three platforms and nothing more: whether the text sizes (12 px for the small lines) are comfortable on the phone, whether the two-line buttons, the red reasons and the yellow focus outline look right, and whether the five rows with the arrows are easy to hit.
- **The real search has only run on this machine's loopback** (a host answering itself). A real Wi-Fi or hotspot with a `tower_server` on another device has not been tried: whether the phone's network lets the broadcast out and the answer in (some Android versions drop broadcasts with the screen off; Wi-Fi with client isolation stops devices seeing each other, `net.md`), and whether the INTERNET permission is all the platform wants. This is the first thing to try: run `tower_server` on one device and open FIND GAMES on the other.
- `LobbyFrame` and `SelectFrame` cannot run without raylib. The logic they call is tested; the glue (the order of the calls, switching screens, the fade-in, the clock reset) is not. A finger still down from a button press does not count as a new tap on the next screen (`Input_NewTap` reports a touch once), but it was not seen.
- The browser build has no search: FIND shows why. Hosting and joining need a typed address and a transport the browser has; neither is decided (`net.md`).
- The lobby comes first only; coming back to it after a run is not built.

## Fixes and Problems

- **A test expected the wrong number:** six steps down the list from the first game land on the seventh, not the sixth. The test was wrong, not the code; it now checks five steps and then one more.
- **One mutation survived the first version of the tests:** removing the clamp on the number of games the backend reports. The loop that fills the table has its own limit, so nothing the old checks looked at changed; but the clamp is what bounds the number of questions asked of a backend that reports a huge count. A check was added (a backend reporting 30 games with one gone is asked about exactly 16).
